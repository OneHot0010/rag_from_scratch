# RAG 切分策略对比与参数建议

> 阶段3 产出。系统梳理 RAG 索引阶段「切分(Chunking)」环节的常用策略,
> 给出可横向对比的实验结论与工程选型/调参建议。
> 切分是检索的**上游**:切错了,后面所有检索策略都在低质量原料上打转。

---

## 0. 为什么切分如此关键

RAG 的召回质量首先取决于「原料」——即 chunk 的质量:

- **chunk 过大**:检索命中后,上下文里混入大量无关内容,噪声高、稀释关键信息,也更费 token。
- **chunk 过小**:语义被切断,单个片段信息不完整,"答案跨块" 时召回不全。
- **切分点粗暴**:在句子/词语中间硬切,破坏语义边界,Embedding 质量下降。

**核心原则:切分要顺着文档自身的结构走(respect structure),而不是无脑按固定字数切。**
粒度(chunk_size)、重叠(overlap)、结构完整性三者需要平衡。

---

## 1. 策略谱系

本项目在 `ragcore/splitters/` 下实现了 6 种可插拔策略(开闭原则:新增策略=新增一个子类+注册,不改核心流程):

| 策略 | 名称 | 切分思路 | 是否需 API |
|---|---|---|---|
| 固定长度 | `fixed` | 定长滑窗 + overlap,最简兜底 | 否 |
| 递归字符 | `recursive` | 按分隔符优先级(段→行→句→词)递归切,尽量保住语义边界 | 否 |
| 句子 | `sentence` | 按句末标点切句,再贪心合并到 chunk_size | 否 |
| 段落 | `paragraph` | 按空行分段,超长段落回退句子切分 | 否 |
| Markdown | `markdown` | 按标题层级切,注入 `heading_path` 上下文锚点 | 否 |
| 语义 | `semantic` | 句间 Embedding 相似度骤降处断开(话题转移点) | 是 |

---

## 2. 对照实验结论

实验脚本:`experiments/compare_splitters.py`。在同一份文档上跑遍所有策略,
输出 chunk 数、长度分布(min/avg/max)、长度标准差(越小越均匀)与样例。

以 `sample.txt`(860 字符,chunk_size=200 / overlap=40)为例:

| 策略 | chunk 数 | min | avg | max | 长度 std | 特点 |
|---|---|---|---|---|---|---|
| fixed | 6 | 59 | 176 | 200 | 52.5 | 长度上界最严格,但尾块偏短、可能切断语义 |
| recursive | 6 | 143 | 174 | 236 | **29.1** | 长度最均匀,语义边界保持好——**通用默认** |
| sentence | 7 | 66 | 158 | 197 | 41.2 | 句子完整,块数偏多、尾块偏短 |
| paragraph | 6 | 143 | 175 | 237 | 29.4 | 段落完整,块数少;依赖清晰的空行分段 |
| markdown | 6 | 143 | 174 | 236 | 29.1 | 结构化文档下额外带标题路径元数据 |
| semantic | 3 | 251 | 288 | 344 | 40.3 | 按话题聚合,块最少、主题内聚最强,但需 API 且较慢 |

> 关键观察:
> - `recursive` 的长度标准差最低(29.1),说明块最均匀,这也是它作为通用默认的原因。
> - `semantic` 块数最少、块最大,把"同一话题"聚在一起,主题内聚性最好,但速度/成本代价高。
> - `fixed` 严格受 chunk_size 约束(max=200),但尾块可能过短(min=59)且会切断语义。
> - `markdown` 在纯文本上退化为与 recursive 近似;它的价值在**结构化文档**上——`heading_path` 元数据能显著改善"脱离标题的裸段落"召回。

## 3. 策略选型:按数据类型选择

| 数据类型 | 首选策略 | 理由 |
|---|---|---|
| 结构清晰的 Markdown / 技术文档 | `markdown` | 顺标题层级切,保留标题路径,召回可溯源到章节 |
| 段落分明的散文 / 报告 / 政策文档 | `paragraph` | 段落即天然语义单元,块完整 |
| 无明显结构的长文本 / 通用兜底 | `recursive` | 长度均匀、语义边界保持好,几乎适配一切 |
| 问答对 / FAQ / 短句密集 | `sentence` | 句子粒度对齐问答粒度,检索精准 |
| 主题跳跃、话题混杂的长文 | `semantic` | 按话题聚合,主题内聚最强(接受 API 成本时) |
| 极简 Demo / 无依赖场景 | `fixed` | 零依赖、最快,可接受语义被切断 |

**经验法则**:不知道选什么,就用 `recursive`;文档有清晰 Markdown 结构就上 `markdown`;
对召回质量要求高且预算充足,再考虑 `semantic`。

## 4. 参数调优建议(chunk_size / overlap)

| 场景 | chunk_size | overlap | 说明 |
|---|---|---|---|
| 中文通用文档 | 300~500 | 50~80 | 兼顾语义完整与检索精度(本项目默认 300/50) |
| 精准问答 / FAQ | 150~300 | 30~50 | 小块提升检索精度,overlap 防关键信息被切断 |
| 长文档 / 摘要类 | 500~1000 | 80~150 | 大块保上下文完整,适合需要整体理解的任务 |
| 代码 / 结构化 | 按结构 | 0~小 | 顺函数/类/标题边界切,overlap 可小甚至为 0 |

调参要点:

1. **overlap 一般取 chunk_size 的 10%~20%**。太小易切断跨块信息,太大则冗余、抬高存储与 token 成本。
2. **chunk_size 与 Embedding 模型的最优输入长度匹配**:过长会稀释向量语义。
3. **先固定策略调 size/overlap,再横向比策略**。用 `compare_splitters.py` 观察长度 std 与块数,std 越低越均匀。
4. **中英文差异**:中文信息密度高,同样字符数承载信息更多,chunk_size 可比英文场景略小。
5. `semantic` 的 `breakpoint_percentile`(默认 90)控制切分敏感度:调低→切得更碎、块更多;调高→块更大、更聚合。

---

## 5. 复现实验

```bash
# 默认 sample.txt,chunk_size=200 / overlap=40
python experiments/compare_splitters.py

# 指定文档与参数
python experiments/compare_splitters.py path/to/doc.md --size 300 --overlap 50

# 每策略多展示几个样例 chunk
python experiments/compare_splitters.py --samples 3
```

> 未配置 API Key 时,`semantic` 会自动跳过,其余 5 种离线策略照常对比。
