# 工业级 RAG 常用检索策略总结

> 面向企业级落地，系统梳理 RAG 中「检索（Retrieval）」环节的常用策略。
> 检索是 RAG 质量的第一决定因素——「检索不到」或「检索错」，再强的生成模型也救不回来。
> 本文按「切分/索引 → 检索前 → 检索中 → 检索后 → 架构级」组织，并给出选型建议。

---

## 0. 全景速览

一次工业级检索通常是多种策略的**流水线组合**，而非单一手段：

```
文档 → ⓪ 切分 & 存储（索引阶段，决定检索的「原料」质量）
                    │
Query               ▼
  │  ① 检索前：查询改写 / 扩展 / 意图路由
  ▼
[ 检索中 ]
  ├─ 向量检索（Dense）
  ├─ 关键词检索（Sparse / BM25）
  └─ 结构化检索（Text-to-SQL / 元数据过滤）
  │  ② 融合（RRF / 加权）
  ▼
  ③ 检索后：Rerank 重排 / 压缩 / 去重
  ▼
Top-K 上下文 → 生成
```

> 切分是检索的**上游**：切错了，后面所有检索策略都在低质量原料上打转。故先谈切分与存储。

---

## 1. 不同类型文档的切分与存储策略（索引阶段）

**核心原则**：切分要**顺着文档自身的结构走**（respect structure），而不是无脑按固定字数切。切分粒度与检索粒度、上下文完整性三者要平衡。

### 1.1 通用切分方法谱系

| 方法 | 思路 | 优点 | 缺点 / 适用 |
|---|---|---|---|
| **固定长度（Fixed-size）** | 按字符/token 数切，带 overlap | 简单、可控 | 会切断语义；仅适合结构弱的纯文本兜底 |
| **递归字符切分（Recursive）** | 按分隔符优先级递归切（段落→句子→词） | 尽量保住语义边界，通用性强 | 仍是「结构无关」的近似 |
| **结构感知（Structure-aware）** | 按文档天然结构切（标题、章节、表格、代码块） | 语义完整、可带层级元数据 | 需按格式定制解析 |
| **语义切分（Semantic）** | 按句间语义相似度断点切 | 主题内聚 | 需额外 embedding 计算，较慢 |
| **父子/滑窗** | 小块检索、大块喂给 LLM | 精度+完整性兼得 | 存储与编排更复杂 |

### 1.2 按文档类型的切分建议

| 文档类型 | 推荐切分方式 | 关键要点 | 建议保存的元数据 |
|---|---|---|---|
| **纯文本 / TXT** | 递归字符切分 + overlap | 无结构，靠分隔符兜底；overlap 防语义断裂 | source、chunk_id |
| **Markdown / 富文本** | 按标题层级（H1/H2/H3）切 | 保留标题路径作为上下文锚点 | 标题层级路径（如 `安装>依赖`） |
| **PDF / Word（长文档）** | 按章节/标题结构切 + 父子块 | 处理分栏、页眉页脚、跨页段落；图表单独抽取 | 页码、章节标题、层级 |
| **HTML / 网页** | 按 DOM 结构（标签）切，剥离导航/广告 | 正文抽取（去模板噪声）是关键 | URL、标题、DOM 路径 |
| **表格（Excel / CSV）** | **行级切分**：每行拼 `列名: 值`；宽表按列分组 | 保留表头语义；聚合/计算类不走切分，走 Text-to-SQL | sheet 名、行号、表名锚点 |
| **代码** | 按语法单元（函数/类）切，勿从中间断 | 用 AST/语言感知切分；保留 import 上下文 | 文件路径、函数/类名、语言 |
| **PPT / 幻灯片** | 按页（slide）切 | 每页标题+正文合并；讲者备注单独存 | 页号、标题 |
| **QA / FAQ / 对话** | 一问一答为一个 chunk | 天然语义单元，不要拆散问答对 | 问题 ID、分类 |
| **法律/合同/规范** | 按条款（条/款/项）切 | 条款是原子单元，编号必须保留 | 条款编号、文件版本 |

### 1.3 切分参数经验值

- **chunk_size**：通用文本 ~200–500 token；QA/条款按自然单元不定长；长文档父块可 1000+ token。
- **overlap**：约 chunk_size 的 10%–20%，防止关键信息被切分点截断。
- **上限保护**：单 chunk 过长会稀释检索信号、超 embedding 上限；过短则语义断裂。二者都要设阈值。

### 1.4 「如何保存」——存储与索引设计

切分产物不是只存正文，工业级要存成**「正文 + 向量 + 元数据」三位一体**，且常需多份表示：

1. **统一数据契约**：每个 chunk = `{ content, embedding, metadata }`。metadata 至少含 `source / 位置（页/行/条款）/ chunk_id / 层级路径`，进阶含版本、更新时间、owner、权限标签（供行/列级 ACL 与溯源）。
2. **存储载体选型**：
   - **向量库**（Chroma / Milvus / Qdrant / pgvector）：存向量 + 元数据，做 ANN 检索；
   - **倒排索引**（Elasticsearch / OpenSearch）：存原文做 BM25，支撑混合检索；
   - **原文档存储**（对象存储/DB）：存父块或原始文件，供父子块检索「小检索、大返回」。
3. **多表示索引（Multi-representation）**：为同一父块额外索引其**摘要 / 假设问题 / 关键词**等，用它们检索、返回父块，提升召回角度。
4. **父子映射**：子块 metadata 里存 `parent_id`，检索命中子块后回查父块喂给 LLM。
5. **增量与去重**：按**文件指纹 + chunk 主键**做增量更新，避免每次全量重建；文档更新时按 source 精准替换其所有 chunk。
6. **版本与可溯源**：保留文档版本号，回答时能定位「哪个版本、哪一页/条」。

> **一句话**：切分「顺结构」，存储「带元数据、多表示、可增量、可溯源」。切分与存储决定了检索的天花板。

## 2. 检索前策略（Pre-Retrieval：优化「问什么」）

| 策略 | 解决的问题 | 做法 | 代价 |
|---|---|---|---|
| **查询改写（Query Rewriting）** | 口语化、指代不清、多轮省略 | 用 LLM 把「它多少钱」改写成「iPhone 15 的价格」 | 增加一次 LLM 调用延迟 |
| **查询扩展（Query Expansion）** | 用词与文档不一致（同义词、缩写） | 生成同义/近义查询一起检索；HyDE：先让 LLM 生成一个假设答案再拿它去检索 | 召回变多，可能引入噪声 |
| **多查询（Multi-Query）** | 单一表述召回片面 | 一个问题生成多个不同角度的子查询，结果合并去重 | N 倍检索开销 |
| **查询分解（Decomposition）** | 复杂/多跳问题 | 把「A 和 B 哪个更便宜」拆成两个子问题分别检索 | 编排复杂度上升 |
| **意图路由（Routing）** | 不同问题需要不同数据源/策略 | 判断走向量库、走 SQL、走某个知识域，或直接拒答 | 路由错误会全盘皆错 |

> **企业实践**：查询改写 + 意图路由几乎是标配；HyDE/多查询按召回瓶颈按需引入，注意延迟与成本。

## 3. 检索中策略（Retrieval：优化「怎么找」）

### 3.1 向量检索（Dense Retrieval）
- **原理**：Query 与 chunk 都编码为稠密向量，用余弦/内积做近似最近邻（ANN）搜索。
- **强项**：语义理解、同义改写、跨语言。
- **弱项**：精确匹配（编号、SKU、人名、罕见术语）易漏；数值/逻辑无能为力。
- **工程点**：ANN 索引（HNSW / IVF-PQ）在召回率与速度间权衡。

### 3.2 关键词检索（Sparse Retrieval / BM25）
- **原理**：基于词频的稀疏匹配（BM25、TF-IDF），或学习式稀疏向量（SPLADE）。
- **强项**：精确术语、编号、专有名词、长尾关键词。
- **弱项**：不懂同义、不懂语义。
- **定位**：与向量检索**互补**，是混合检索的另一条腿。

### 3.3 混合检索（Hybrid Search）★工业级主流
- **做法**：并行跑 Dense + Sparse，再融合结果。
- **融合方法**：
  - **RRF（Reciprocal Rank Fusion）**：只看排名不看分数，鲁棒、无需调参，最常用；
  - **加权求和**：需归一化两路分数并调权重，可控但需调参。
- **收益**：语义 + 精确双覆盖，是绝大多数企业 RAG 的默认选择。

### 3.4 结构化检索（Text-to-SQL / 元数据过滤）
- **场景**：表格/数据库类数据，涉及**聚合、排序、计算、精确过滤**（如「华东区 Q1 销量前三」）。
- **做法**：LLM 把自然语言转成 SQL / DSL 直接查库；或用 metadata 做前置过滤（时间、部门、类别）再向量检索。
- **价值**：向量检索的根本短板补齐——它做不了「求和/Top-N/同比」。

## 4. 检索后策略（Post-Retrieval：优化「用什么」）

| 策略 | 作用 | 典型手段 |
|---|---|---|
| **重排（Rerank）** ★ | 初排 Top-N（如 50）用更强模型精排出 Top-K（如 5），大幅提升上下文精度 | Cross-Encoder / bge-reranker / Cohere Rerank；召回广、精排准的「两阶段检索」 |
| **上下文压缩** | 去掉命中片段里的无关句子，省 token、降噪 | LLM 抽取式压缩、LLMLingua |
| **去重 / 多样性** | 避免 Top-K 高度雷同，浪费上下文 | MMR（最大边际相关）平衡相关性与多样性 |
| **上下文重排布** | 缓解「中间迷失」(lost-in-the-middle)，模型更关注首尾 | 把最相关片段放在提示词首尾 |

> **两阶段检索（召回 → 精排）是工业级近乎必备的范式**：召回阶段追求「不漏」（高 recall、便宜），精排阶段追求「不错」（高 precision、用重排模型）。

## 5. 架构级 / 进阶策略（改变「检索什么粒度」）

| 策略 | 核心思想 | 适用场景 |
|---|---|---|
| **父子块检索（Parent-Child / Small-to-Big）** | 用小块检索保证命中精度，返回其所属大块（父块）给 LLM 保证上下文完整 | 长文档、切分粒度两难 |
| **句窗检索（Sentence-Window）** | 按句子检索，返回命中句 ±N 句的窗口 | 精细定位 + 上下文补全 |
| **多向量 / 摘要索引** | 为每个 chunk 额外索引其摘要、假设问题、关键词等多种表示 | 提升召回角度 |
| **层级检索（RAPTOR / 树状摘要）** | 对文档做多层聚类摘要，先粗后细逐层检索 | 超长文档、需要全局概览 |
| **知识图谱检索（GraphRAG）** | 抽取实体-关系构建图谱，沿关系做多跳检索 | 关系推理、多跳问答（「A 的上级的下属」） |
| **Agentic / 迭代检索（Self-RAG / 主动检索）** | 模型自行判断是否需要检索、检索够没、要不要再查一轮 | 复杂推理、开放式任务 |

## 6. 选型建议（从简到繁的演进路径）

1. **起步**：合理切分（顺结构）+ 向量检索 + Top-K —— 快速跑通端到端。
2. **第一次升级**：加 **BM25 → 混合检索 + RRF** —— 通常是性价比最高的一步。
3. **第二次升级**：加 **Rerank 精排（两阶段检索）** —— 上下文精度显著提升。
4. **按数据类型分流**：表格/数值走 **Text-to-SQL / 元数据过滤**，配 **意图路由**；文档按类型用对应切分策略。
5. **按瓶颈补强**：
   - 召回不足 → 查询改写 / 多查询 / HyDE；
   - 上下文断裂 → 父子块 / 句窗 / 改进切分；
   - 关系/多跳 → GraphRAG；
   - 长文档全局 → RAPTOR；
   - 复杂推理 → Agentic 迭代检索。

> **原则**：不要一上来堆满所有策略。**先测评定位瓶颈（召回率 / 精确率 / 端到端答案质量），再针对性加策略**，每加一项都要评估「质量收益 vs 延迟/成本」。

---

## 7. 评估指标（选型的依据）

- **检索层**：Recall@K、Precision@K、MRR、NDCG、命中率（Hit Rate）。
- **端到端**：答案正确性、忠实度（Faithfulness，是否忠于上下文）、答案相关性（可用 RAGAS 等框架）。
- **工程层**：P99 延迟、QPS、单次成本（LLM 调用次数）。

---

## 8. 与本项目的关系

当前项目（阶段 2.1）：切分为**固定长度 + overlap**（`ragcore/splitter.py`），检索为 **向量检索 + Top-K 余弦相似**（`ragcore/vector_store.py`），存储为**内存向量库**，属于第 6 节的「起步」阶段。后续可按演进路径分阶段引入：
- **P1**：按文档类型的结构感知切分；BM25 混合检索 + RRF；表格类问题的 Text-to-SQL 路由；
- **P2**：Rerank 两阶段检索；持久化向量库 + 倒排索引 + 元数据存储；
- **P3**：父子块 / 多表示索引 / GraphRAG 等进阶策略。

本文仅为策略梳理，**未改动任何代码**。
