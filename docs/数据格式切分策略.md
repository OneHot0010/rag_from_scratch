# 企业级 RAG:按数据格式的切分策略总结与实践

> 面向企业落地场景,系统梳理**不同数据格式**在 RAG 索引阶段应采用的切分(Chunking)策略,
> 逐一说明「为什么这么做」;并在其后对我所了解的 RAG 通用切分策略做**详细补充**,
> 给出与本项目 `ragcore/splitters/` 实现的映射、调参与选型建议。
>
> 配套阅读:`docs/切分策略.md`(策略对照实验结论 + 参数建议表)、
> `docs/检索策略.md`(切分作为检索上游的定位)。

---

## 0. 第一性原理:为什么切分必须「因格式而异」

RAG 的召回质量首先由 chunk 的**质量**决定,而 chunk 质量取决于切分是否尊重了数据本身的结构。核心矛盾有三:

1. **粒度矛盾**:chunk 过大 → 检索命中后混入无关内容、稀释向量语义、抬高 token 成本;chunk 过小 → 语义被切断、单块信息不完整、"答案跨块"时召回不全。
2. **边界矛盾**:在句子/表格行/函数体/标题中间硬切,会破坏语义完整性,导致 Embedding 质量下降、检索到"半句话"。
3. **上下文矛盾**:裸段落脱离其标题/章节/表头后,语义不自足(如一个数字脱离了它的列名和行名就毫无意义)。

**结论:切分要顺着数据自身的结构走(respect structure),而不是无脑按固定字数切。**
不同格式的"天然结构单元"不同——散文是段落、Markdown 是标题层级、表格是行、代码是函数/类、PPT 是页——因此切分策略必须因格式而异。这就是企业里"一套固定切分打天下"往往召回差的根因。

## 1. 企业常见数据格式 × 切分策略速查

| 数据格式 | 天然结构单元 | 推荐切分策略 | 关键动作 | 本项目对应 |
|---|---|---|---|---|
| 纯文本 / 长文 | 段落、句子 | 递归字符 / 语义 | 保句边界 + overlap | `recursive` / `semantic` |
| Markdown / 技术文档 | 标题层级 | 结构感知 | 按 `#` 切,注入标题路径 | `markdown` |
| PDF(数字版) | 页、栏、章节 | 版面解析 + 递归 | 先还原阅读顺序,再按结构切 | (需 PDF loader) |
| PDF(扫描件) | 页 | OCR + 版面 + 递归 | 先 OCR,再按块切 | 见 `pdf` 技能 |
| Word / Office | 标题样式、段落 | 结构感知 | 按 Heading 样式切 | (stub loader) |
| HTML / 网页 | DOM、标签语义 | DOM 感知 | 去噪 + 按语义标签切 | (stub loader) |
| 表格(Excel/CSV) | 行、表头 | 行级 + 表头回填 | 每行/若干行成块,携带表头 | `ExcelLoader` 已实现 |
| 代码 | 函数、类、模块 | 语法感知(AST) | 按定义边界切,带签名+docstring | (可扩展) |
| 结构化(JSON/XML) | 节点、记录 | 按记录 / 路径 | 每条记录成块,保留路径 | (可扩展) |
| 日志 | 行、事件 | 按事件 / 时间窗 | 按事务/请求 ID 聚合 | (可扩展) |
| 幻灯片(PPT) | 页 | 按页 + 备注 | 每页成块,合并演讲者备注 | (可扩展) |
| 邮件 / IM 聊天 | 消息、会话 | 按消息 / 会话窗 | 按发件人/话题聚合 | (可扩展) |
| FAQ / 问答对 | Q-A 对 | 按 QA 对 | 一问一答成块,不拆 | `sentence` 近似 |

## 2. 逐格式详解:策略与「为什么」

### 2.1 纯文本 / 长文(散文、报告、政策)
- **策略**:递归字符切分(`recursive`)为通用默认;主题跳跃明显时用语义切分(`semantic`)。
- **为什么**:纯文本没有显式结构标记,只能靠分隔符优先级(段落→换行→句末标点→逗号→空格)递归回退,尽量在**语义边界**处切,避免切断句子。overlap 让相邻块共享尾部句子,防止关键信息卡在切分点被截断。主题混杂的长文用语义切分能把"同一话题"聚在一起,主题内聚性最好。

### 2.2 Markdown / 技术文档
- **策略**:结构感知切分(`markdown`),按 ATX 标题(`#`~`######`)划分小节,为每个 chunk 注入**标题路径**(如 `安装 > 依赖`)写入 metadata;超长小节回退递归切分;代码围栏(``` ``` ```)内的 `#` 不误判为标题。
- **为什么**:Markdown 的标题层级就是作者亲手标注的语义骨架,顺着它切天然对齐主题。标题路径作为"上下文锚点"能解决**裸段落语义不自足**的问题——一段安装说明脱离"安装 > 依赖"标题后,检索时容易与其他章节混淆,带上路径后既提升召回精度又可溯源到具体章节。

### 2.3 PDF
- **策略**:先**版面解析**(layout parsing)还原阅读顺序,识别双栏/页眉页脚/图表/表格,再对正文按章节+递归切分;扫描件先 OCR。
- **为什么**:PDF 是"打印导向"格式,内部文本流的物理顺序常与阅读顺序不一致(双栏尤甚),直接抽取会得到错乱的字符序列。页眉页脚、脚注若不剔除会污染 chunk。表格若按行流抽取会彻底错位,需专门识别。故必须先恢复结构再切。本项目的 `pdf` 技能提供 PyMuPDF + OCR 的轻量解析路径。

### 2.4 Word / Office 文档
- **策略**:利用 Heading 样式(Heading 1/2/3)与段落样式做结构感知切分,思路同 Markdown。
- **为什么**:docx 内含显式的样式层级(比纯文本信息更丰富),标题样式即语义分节点。按样式切比按字数切更贴合作者的组织逻辑,也便于携带"章节路径"元数据。

### 2.5 HTML / 网页
- **策略**:先**去噪**(导航栏、广告、页脚、脚本样式),再按语义标签(`<article>`、`<section>`、`<h1-6>`、`<p>`、`<table>`、`<li>`)切分。
- **为什么**:网页正文往往被大量模板噪声包围,不去噪会让 chunk 充斥无关内容。HTML 的标签本身携带语义(标题/段落/列表/表格),按 DOM 结构切能保留这些边界,比对渲染后纯文本按字数切质量高得多。

### 2.6 表格(Excel / CSV)
- **策略**:**行级切分 + 表头回填**——每行(或每若干行)成一个 chunk,并把列名(表头)拼进每个 chunk;合并单元格需回填值;必要时把整行序列化为"列名: 值"的自然语言。
- **为什么**:表格里单个单元格的值脱离其**行标签与列名**就没有意义(如孤零零一个 `1200` 无法检索)。把表头随每行携带,才能让"某产品某季度的销售额"这类查询命中正确的行。合并单元格在 openpyxl 里只有左上角有值,不回填会产生大量空洞。本项目 `ExcelLoader` 已实现表头识别、合并单元格回填、多 sheet 处理。

### 2.7 代码
- **策略**:**语法感知**(基于 AST 或语言分隔符)按函数/类/方法定义边界切,每块尽量携带函数签名与 docstring;超大函数再内部细分。
- **为什么**:代码的语义单元是函数与类,不是字符。在函数体中间切会得到无法理解的片段。带上签名和 docstring 能让 Embedding 抓住"这段代码做什么"。这也是递归字符切分为代码预置专门分隔符(如 `\nclass `、`\ndef `、`\n\n`)的原因。

### 2.8 结构化 / 半结构化(JSON / XML)
- **策略**:按**记录/节点**切,每条记录成块,保留其在结构中的**路径**(如 `orders[3].items[0]`)或键名作为上下文。
- **为什么**:结构化数据的最小语义单元是"一条记录",跨记录乱切会破坏字段的对应关系。保留路径/键名让值有"名字",既可检索也可溯源回原始结构。

### 2.9 日志
- **策略**:按**事件/事务**聚合——用请求 ID、trace ID 或时间窗把相关日志行归并成块,而非逐行。
- **为什么**:单行日志信息量极低且高度重复,逐行切会产生海量近重复 chunk、稀释检索。按一次请求/一个事务聚合,chunk 才承载完整"发生了什么"。

### 2.10 幻灯片(PPT)
- **策略**:**按页成块**,合并该页的标题、正文与演讲者备注(speaker notes);必要时把图表的替代文本(alt text)纳入。
- **为什么**:PPT 的语义单元是"一页",一页表达一个要点。演讲者备注常含关键解释信息,合并后 chunk 更完整。跨页切会割裂一个论点。

### 2.11 邮件 / IM 聊天记录
- **策略**:按**消息或会话窗口**切,携带发件人、时间、主题;长会话可按话题分段。
- **为什么**:对话是多轮、多人的,脱离"谁在何时说了什么"就无法理解。按消息保留元数据、按话题聚合窗口,既能定位到具体发言又保留上下文。

### 2.12 FAQ / 问答对
- **策略**:**一问一答成块**,绝不拆开 Q 与 A。
- **为什么**:QA 对是天然的最小自足语义单元,问题即天然的"检索锚",答案紧随其后。拆开会让答案脱离问题、失去可检索性。

## 3. RAG 切分策略详细补充(通用方法谱系)

除了上面"按格式选策略",还有一层**与格式正交的通用切分方法论**。以下是我所了解的、当前工业界主流与前沿的切分策略,可与格式策略叠加使用。

### 3.1 基础策略族(本项目已实现)

| 策略 | 思路 | 优点 | 局限 / 适用 |
|---|---|---|---|
| 固定长度 `fixed` | 定长滑窗 + overlap | 零依赖、最快、可预测 | 无视语义,会切断句子;仅作兜底 |
| 递归字符 `recursive` | 按分隔符优先级递归回退切分 | 长度均匀、保住语义边界,**通用默认** | 不感知文档高层结构 |
| 句子 `sentence` | 按句末标点切句 + 贪心合并 | 句子完整,粒度对齐问答 | 块偏多、尾块偏短 |
| 段落 `paragraph` | 按空行分段,超长回退句子 | 段落完整、块数少 | 依赖清晰的空行分段 |
| 结构感知 `markdown` | 按标题层级切 + 注入标题路径 | 保结构、可溯源、上下文自足 | 仅适用有显式结构的文档 |
| 语义 `semantic` | 句间 embedding 相似度骤降处断开 | 主题内聚最强 | 需 API、较慢、有成本 |

### 3.2 进阶策略(建议后续演进方向)

- **父子 / 小块检索大块返回(Parent-Child / Small-to-Big)**:用**小块**做向量检索以提升命中精度,命中后返回其**所属父块(大块)**给生成模型以保证上下文完整。兼顾"检索精准"与"上下文充足",是工业界最常用的高性价比技巧之一。

- **句子窗口检索(Sentence-Window)**:以单句为索引单元,命中后把该句**前后各 N 句**一并返回。是 Parent-Child 的轻量特例,特别适合精准问答。

- **层级切分(Hierarchical / Multi-granularity)**:同一文档同时切成多个粒度(句/段/节/文档),建多层索引,检索时可跨粒度召回。适合结构深、篇幅长的文档。

- **命题式切分(Proposition-based)**:用 LLM 把文本改写成一组**自足的原子命题**(每条是一个独立事实句),以命题为检索单元。召回精度高,但预处理成本大(需逐段调 LLM)。

- **上下文增强切分(Contextual Retrieval)**:切块后,用 LLM 为每个块生成一句"该块在全文中的位置/背景"描述并前置,再做 embedding 与 BM25。显著降低"脱离上下文的块"召回失败率,代价是索引期额外 LLM 调用。

- **Late Chunking(后切分)**:先对**长文整体**做 embedding(长上下文编码器),让每个 token 的向量都吸收全文上下文,之后再在向量层面切块并池化。缓解"块级 embedding 丢失全局上下文"的问题,依赖支持长上下文的 Embedding 模型。

- **Agentic Chunking(智能体切分)**:让 LLM 像人一样通读文档、自主判断在哪里切、如何组织块。质量上限高,但成本与延迟最高,适合高价值、量不大的文档。

### 3.3 与检索/存储的协同

切分不是孤立环节,需与下游协同设计:

- **overlap** 是切分层面的"跨块信息保险",而 Parent-Child、句子窗口是检索层面的补偿——两者可叠加。
- 结构感知切分产出的**元数据(标题路径、页码、行号、发件人)**,应写入向量库供**元数据过滤**与**混合检索(BM25 + 向量 + RRF)**使用,并支撑召回结果**溯源**。
- 切分粒度应与 Embedding 模型的最优输入长度、以及生成模型的上下文预算联动。

## 4. chunk_size / overlap 调参建议

| 场景 | chunk_size | overlap | 说明 |
|---|---|---|---|
| 中文通用文档 | 300~500 | 50~80 | 兼顾语义完整与检索精度(本项目默认 300/50) |
| 精准问答 / FAQ | 150~300 | 30~50 | 小块提精度,overlap 防关键信息被切断 |
| 长文档 / 摘要类 | 500~1000 | 80~150 | 大块保上下文完整,适合整体理解 |
| 代码 / 结构化 | 按结构切 | 0~小 | 顺函数/记录边界,overlap 可小甚至为 0 |

要点:
1. **overlap 取 chunk_size 的 10%~20%**——太小易切断跨块信息,太大则冗余抬升成本。
2. **中文信息密度高**,同字符数承载信息更多,chunk_size 可比英文场景略小。
3. **先固定策略调 size/overlap,再横向比策略**;用 `experiments/compare_splitters.py` 观察长度标准差(越低越均匀)与块数。
4. `semantic` 的 `breakpoint_percentile`(默认 90)控制敏感度:调低→切得更碎,调高→块更大更聚合。

## 5. 选型决策路径(速查)

```
文档有清晰标题结构(Markdown/Word)?  ──是──▶ markdown / 结构感知(注入标题路径)
        │否
表格 / CSV / Excel?                 ──是──▶ 行级切分 + 表头回填
        │否
代码?                                ──是──▶ 语法感知(按函数/类,带签名)
        │否
段落分明的散文/报告?                 ──是──▶ paragraph
        │否
问答对 / FAQ?                        ──是──▶ 按 QA 对(一问一答成块)
        │否
主题跳跃、话题混杂的长文?             ──是──▶ semantic(预算充足时)
        │否
其它 / 不确定?                       ──────▶ recursive(通用默认)

对召回质量要求高时,在上述任意策略之上叠加:
  Parent-Child(小块检索、大块返回) 或 句子窗口 或 Contextual Retrieval。
```

**一句话经验法则**:不知道选什么就用 `recursive`;有结构就上 `markdown`;表格必带表头;代码按函数切;要更强召回再叠加父子/上下文增强。

## 6. 与本项目的映射

- 已实现的 6 种策略均在 `ragcore/splitters/`,通过 `registry.build_splitter(name, ...)` 按名分派,新增策略=新增子类+注册,不改核心流程(开闭原则)。
- 表格格式的切分能力体现在 `ragcore/loaders/excel_loader.py`(表头回填、合并单元格、多 sheet)。
- 运行 `python experiments/compare_splitters.py` 可在同一文档上横向对比各策略指标。
- 后续演进(Parent-Child / 上下文增强 / 混合检索)属于阶段6"检索策略"范畴,详见 `docs/检索策略.md`。
